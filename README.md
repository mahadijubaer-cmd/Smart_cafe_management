# SCMS — Smart Cafe Management System

SCMS is a multi-tenant SaaS platform for running food-service operations — independent
restaurants, university/corporate cafeterias, franchise chains, and multi-vendor food
courts — from a single system. It covers the full order lifecycle: digital menus, QR/table
ordering, kitchen order queues, inventory and stock control, cleaning workflows, staff and
role management, real-time notifications, and analytics/reporting — all served from one
codebase, isolated per organization ("tenant").

A single deployment can host any number of independent organizations. Each one gets its own
branded ordering page, staff console, menu, tables, inventory, and user base, addressed by a
unique URL slug (e.g. `/bracu`, `/unimart-hall`), while sharing the same application and
database.

## 1. System Overview

SCMS solves the same operational problem for very different kinds of food-service
businesses: how to take an order (in person, by QR code, or as a walk-in guest), route it to
the kitchen, track it through preparation and fulfillment, manage what's in stock, and give
managers visibility into what's happening — while keeping every organization's data
completely separate from every other organization's.

The platform recognizes several **organization types** ("tenant types"), each with tailored
workflows:

| Tenant type | Typical use case |
|---|---|
| `independent_restaurant` | A single standalone restaurant or café |
| `academic` | A university/college cafeteria |
| `corporate` | An office cafeteria |
| `franchise_brand` / `franchise_outlet` | A multi-branch chain with a parent brand and self-service outlets |
| `food_court` / `food_court_vendor` | A shared physical space with multiple independent vendors and shared seating |

On top of tenant type, each organization is assigned a **subscription tier**
(`free`, `starter`, `professional`, `enterprise`) that governs feature and usage limits.

A **platform administration layer** sits above all tenants — used by the platform operator
to onboard organizations, monitor subscriptions, and audit activity across the whole system.

## 3. Architecture

### Multi-tenancy model
SCMS uses **row-level multi-tenancy**: all tenants share one application and one database,
and every tenant-scoped table carries a `tenant_id` column. Isolation is enforced at the
application layer rather than through separate databases per tenant, which keeps operations
simple while still giving each organization a fully private dataset.

- A tenant-context middleware resolves the tenant from the authenticated request (via JWT
  claims) and attaches a tenant context (tenant ID, tenant type, tenant slug, outlet ID) to
  every request.
- Every protected endpoint depends on this context to filter and authorize data access, so
  a request authenticated for one organization can never read or write another
  organization's data.
- JWTs carry tenant claims directly (tenant ID, tenant type, role, and — where relevant —
  outlet ID for franchise setups), so authorization does not require an extra database
  round-trip on every request.

### Routing model
The frontend mirrors the tenant model in its URL structure:

- `/[tenant_slug]/...` — the tenant-scoped application (login, ordering, staff console,
  admin console, cleaner console, food-court console), e.g. `/bracu/menu`,
  `/bracu/dashboard`.
- `/m/[public_slug]/...` — public, unauthenticated guest ordering (QR-code table ordering
  with no login required).
- `/discover` — a public directory for finding an organization's ordering page.
- `/register-organization` — public self-service onboarding for new organizations.
- `/(platform)/admin/...` — the platform-operator console (tenant management, subscriptions,
  system-wide analytics, audit log), not scoped to any single tenant.

### Real-time updates
A WebSocket endpoint (`/ws/{user_id}`, authenticated by JWT) keeps staff and kitchen screens
live without polling. Each connection is registered per tenant and subscribed to that
tenant's Redis pub/sub channel; backend events (new order placed, order status changed,
low-stock alert, etc.) are published to Redis and pushed to every connected client for that
tenant in real time.

### Role-based access control
Access to every module is governed by a role attached to the authenticated user's JWT.
Representative roles include: guest/`customer`, `student` (academic ordering role),
`staff`, `server` (food-court floor runner), `cleaner`, `outlet_admin`, `tenant_admin`,
`food_court_admin`, and `platform_admin`. Each role is scoped to see and act only on the
functionality relevant to it.

## 5. Core Functionality

- **Digital menu management** — categories, items, pricing, availability toggles, and
  branding per organization.
- **Ordering** — dine-in via QR-coded tables, staff-assisted ordering, and fully public
  guest ordering (no account required) for food-court and quick-service settings.
- **Kitchen order queue** — live, real-time view of incoming and in-progress orders for
  kitchen/staff, with status transitions (placed → preparing → ready → served/completed).
- **Table & floor-plan management** — a drag-and-drop floor-plan editor, QR code generation
  per table, and table-level order tracking.
- **Inventory management** — stock levels, purchase orders, low-stock alerts, and (for
  franchise setups) centralized inventory across outlets.
- **Cleaning workflow** — a dedicated queue for cleaning staff to see and clear tables that
  need attention after service.
- **Staff & user management** — role-based invitations, account management, and
  organization-scoped permissions.
- **Notifications** — real-time, in-app notifications pushed over WebSocket (new orders,
  status changes, low stock, invitations).
- **Receipts & institutional memos** — PDF generation for order receipts and (for academic
  tenants) institutional billing memos.
- **Analytics & reporting** — sales, order-volume, and operational dashboards, scoped to the
  organization (and, for platform admins, across the whole platform).
- **Food-court mode** — a shared floor and shared tables across multiple independent
  vendors within one physical location, with per-vendor order attribution and a unified
  customer-facing menu.
- **Franchise support** — a parent brand with multiple self-service outlets, each with its
  own staff and inventory but shared branding and oversight.
- **Self-service organization onboarding** — any eligible business type can register itself
  and get a live ordering page in minutes, without platform-operator intervention.
- **Platform administration** — a control plane for the platform operator to manage
  tenants, subscription tiers, platform-wide analytics, and a system audit log.

## 6. Getting Started

The full stack (database, cache, API, and web app) runs locally via Docker Compose from the
`Smart_cafe_management/` directory:

```bash
# 1. Copy and configure environment variables
cp .env.example .env

# 2. Start all services (postgres, redis, backend, frontend)
docker compose up --build -d

# 3. Apply database migrations
docker compose exec backend alembic upgrade head

# 4. Run the test suite (optional)
docker compose exec backend pytest -v
```

| Service | Purpose | Local URL |
|---|---|---|
| PostgreSQL | Primary database | `localhost:5433` |
| Redis | Cache & real-time pub/sub | `localhost:6379` |
| Backend (FastAPI) | REST API + WebSocket | `http://localhost:8001` |
| Frontend (Next.js) | Web application | `http://localhost:3000` |

Interactive API documentation is available at `http://localhost:8001/docs` once the backend
is running.

> The application uses slug-prefixed routing — there is no bare `/login`. Visit
> `/discover` to find an organization, or `/register-organization` to create a new one.

Required environment variables (database connection, JWT secret, Redis URL, email provider
keys, etc.) are defined in `backend/app/core/config.py`; provision your own values for any
environment you run — no credentials are included in this repository.

Full deployment and testing instructions: [specs/operations/deployment.md](specs/operations/deployment.md)
and [specs/operations/testing.md](specs/operations/testing.md).

## 7. User Guide — Module by Module

### 7.1 Getting In
Every organization has its own sign-in page at `/{organization-slug}/login`. New
organizations are created via **Register Organization** (`/register-organization`), a
three-step wizard: choose a category → enter organization details (name, URL slug, city,
brand colour, contact email) → create the first admin account. This creates the
organization and its first administrator in one step.

If you don't know an organization's slug, use **Discover** (`/discover`) to search for it
by name or category.

### 7.2 Guest / Customer Ordering
- **QR table ordering** — scanning a table's QR code opens that table's menu directly
  (`/{slug}/menu` when signed in, or the public guest flow at `/m/{public_slug}` when not).
  No account is required for guest ordering.
- **Cart & checkout** — add items to a cart, review it in the cart sidebar, and place the
  order against the scanned table.
- **Order tracking** — after placing an order, a live tracking page shows its status in
  real time (placed → preparing → ready → served) without needing to refresh.
- **Wallet / order history** (signed-in customers) — past orders and balances are visible
  from the customer account area.

### 7.3 Staff Console
- **Kitchen queue** — a live board of incoming and active orders, with one-tap status
  updates as items move through preparation.
- **Menu availability** — staff can mark items as sold-out/available in real time without
  editing the underlying menu.
- **Table status** — see which tables are occupied, awaiting service, or need cleaning.

### 7.4 Cleaner Console
A focused queue showing only tables that need cleaning after service, with a single action
to mark a table clean and ready for the next guest.

### 7.5 Admin Console (Organization Administrator)
- **Dashboard** — an at-a-glance operational summary for the organization.
- **Menu management** — create/edit categories and items, set prices, and manage
  availability.
- **Table & floor-plan management** — drag-and-drop layout editor; generate and print
  per-table QR codes.
- **Inventory management** — track stock levels, record purchase orders, and get low-stock
  alerts.
- **User management** — invite staff/cleaners/other admins and manage their roles.
- **Outlets** (franchise brands only) — manage multiple outlets under one brand.
- **Public ordering link** — get the shareable/QR link for guest ordering.
- **Reports & analytics** — sales and order trends for the organization.
- **Memos** (academic tenants) — generate institutional billing memos as PDFs.

### 7.6 Food Court Console
For shared, multi-vendor spaces:
- **Unified menu** — customers browse a single combined menu spanning all vendors at the
  location.
- **Shared tables** — table/floor management is shared across vendors, with clear per-vendor
  order attribution.
- **Vendor analytics** — per-vendor and food-court-wide sales insight.

### 7.7 Platform Administration
Reserved for the platform operator (not scoped to any single organization):
- **Tenant management** — view and manage all organizations on the platform.
- **Subscriptions** — monitor and adjust subscription tiers.
- **Platform analytics** — usage and activity across all tenants.
- **Audit log** — a system-wide record of significant administrative actions, for
  accountability and troubleshooting.

### 7.8 Notifications
All roles receive real-time, in-app notifications relevant to their work (new orders,
status changes, low-stock warnings, staff invitations) delivered instantly over a live
connection rather than by polling or refreshing the page.
